# Grouping does not travel in the archive

[0032](0032-archive-preserves-inputs-not-derived-state.md) puts transaction grouping in
tier 1, and says why in one sentence: "No rule exists that could reconstruct it."
[0041](0041-server-owns-transaction-grouping.md) built that rule.
[0097](../issues/0097-server-side-transaction-grouping.md) records that it reads stored
data and fetches nothing, which is 0032's own definition of tier 3 -- cheap, and
excluded.

**The archive carries postings, not groups.** A `TxWindow` holds its postings directly,
and the partition is recomputed on import from the evidence the postings carry
([0042](0042-grouping-evidence-in-the-standard-format.md)).

The group level does not shrink, it goes. Every other aggregate root in the format
carries fields of its own -- an instrument has its identifier, asset class and coverage,
a statement its account and date -- and 0077 deliberately gave a tx group neither an id
nor a timestamp, because both are generated by the importing instance. So the tx group
is a level whose entire payload is the partition, and once the partition is derived
there is nothing left in it. [0035](0035-archive-nests-by-aggregate-root.md) admits a
level only for what cannot vary between rows below it; a level with no fields at all
never met that test, and only looked like it did while the partition was data.

The upload format follows, because it is the same message. One schema in both
directions is what [0034](0034-archive-format-is-its-own-proto-package.md) and
[0078](../issues/0078-archive-format-proto-package.md) are for, and a nested export
beside a flat upload would need a second reader for a shape that is about to be deleted.

## group_ref survives the format change

The server does not group yet, so between the format move and the engine the file still
has to say what the converter decided. It says it as an optional `group_ref` on the
posting: file-scoped, never stored, and exactly what the flat CSV always carried.
[0098](../issues/0098-retire-converter-side-grouping.md) deletes the field, and nothing
else about the format changes when it does.

Keeping it is not a concession. [0097](../issues/0097-server-side-transaction-grouping.md)
validates the engine by running it in shadow and requiring it to reproduce `group_ref`
exactly, so the field has to outlive the format move regardless of what the archive
would prefer.

## Considered: the archive records a partition the importer honours

The alternative is to keep the group level as a record of the last accepted partition,
and have import take it as given rather than regroup. It survives an engine regression
and it restores data ingested before evidence was captured, which regrouping does not.

It was rejected because it reinstates exactly what 0041 removed: two things that decide
the partition, one of them a file. The importing server would either honour the file and
hold data it cannot explain from evidence, or regroup and silently disagree with what
the file says. Neither is better than not carrying it, and the first is the two-rule-sets
outcome 0041 turned down when the second rule set was a converter.

## Consequences

**Routed residuals stop being exported.** 0077 exports `IMBALANCE`,
`TRANSFER_CLEARING` and `SOURCE_ROUNDING` postings, and the round trip is idempotent
because a group exported with its residual already sums to zero and `routeResiduals`
skips it. That argument is about a partition that survives the trip. A residual carries
no correlation evidence of its own, so once the importer regroups it has nothing to say
which postings it belongs with. It joins the synthetic `INITIALIZE` postings in 0032's
tier 3 and is routed fresh after the grouping pass, at 0098 rather than now.

**A human assertion is still tier 1.** What 0041 leaves open -- how a hand-made grouping
or transfer match is replayed when group ids churn -- is an input, not a partition, and
an archive that drops the partition still has to carry it. It travels as the assertion it
is, alongside the postings, not as a shape imposed on them.
