Retire the standard transaction CSV and have converters produce archive messages
instead.

## Motivation

The standard transaction CSV is the most heavily used format in the repository
and the one with the least reason to be a CSV. It is machine-written by
converters and machine-parsed by client/lib/csv/standard.ts; no human reads it
and no pipeline consumes it downstream. Its claim is inertia.

Meanwhile it is lossy against its own API. `Tx.identifier_hints` is a repeated
`InstrumentIdentifier` but the file carries at most one hint per row. `broker`,
the period and `share_count_basis` are carried by the upload request rather than
the file, so an upload is not self-describing.

## Design

Converters already return `StandardParseResult` -- an envelope of txs, period
bounds and `share_count_basis` -- rather than CSV text, so the object model is
most of the way there. What changes is which serialiser the file path uses.

The transaction part flattens first, in both directions.
adr/0043-grouping-does-not-travel-in-the-archive.md drops the group level: a tx
group has no fields of its own, and once the server derives the partition
(adr/0041-server-owns-transaction-grouping.md) there is nothing left in the level
to state. `TxWindow` holds its postings directly. The export written under 0077
nests today, and moving it is a prerequisite rather than a separate change --
there is one message and it serves both directions, so a nested export beside a
flat upload would need a second reader for a shape that is about to be deleted.

Grouping travels until the engine lands as an optional `group_ref` on the
posting: file-scoped, never stored, and what the CSV always carried. 0098 deletes
the field and nothing else about the format changes when it does. It has to
outlive this issue regardless, because 0097 validates the engine by requiring it
to reproduce `group_ref` exactly.

Consequences that fall out:

- A posting can carry several identifier hints.
- `broker`, period and `share_count_basis` move into the file, and
  `share_count_basis` is per posting rather than per upload, for the reason 0077
  moved it off the window.
- The paired-presence validation that `exchange` requires `exchange_type` and
  back goes with the columns; `identifier_type` already says whether the domain
  is a MIC or an OpenFIGI code, so `exchange_type` was redundant.
- `UpsertTxsRequest` collapses into a `TxWindow` plus a filename. `broker`,
  `source`, the period and the tx list are what a window already says, so the
  upload path and the archive import path meet above `ingestBatch` rather than
  each assembling their own call.

Retire client/lib/csv/standard.ts and its tests, and the transaction CSV section
of docs/spec/csv-format.md, which is then empty and can be deleted.

## Downstream

The conversion is wider than the repository. `local/scripts/convert-fidelity.py`,
`convert-ibkr.py` and `convert-schwab.py` write these column names, as do the
masters in `local/standard-format/`; those are regenerated by re-running the
scripts. Every CSV fixture under e2e/fixtures/ is in this format and moves with
it.

The browser extension imports the same converters through its tsconfig path
alias and is affected by whatever they return, so it moves with them.

The broker-file upload UI is unaffected: converters still read Fidelity CSV,
IBKR OFX and Schwab CSV, which are the brokers' own formats. Only the standard
format in between is replaced.
